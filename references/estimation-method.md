# 拆解与估算口径

本文说明从输入到工作量评估行的判断规则。基线工作簿（任务目录、修正因子、估算参数）是唯一权威，
本文只描述如何使用它，不复制任何基线数值。

## 1. 从输入到任务行

一行任务 = 一件可交付、可验收的做事内容。判断顺序：

1. **PRD 定范围**：每个需求条目对应至少一行任务；同一需求覆盖多个实现单元（多个页面、多个接口、
   多类工作）时拆成多行。
2. **HLD 定实现**：接口清单决定 API、集成、消息与批处理类子任务类型；
   技术选型与部署章节决定工程化类子任务类型；领域模型决定后端任务里要写清哪些存储与数据处理内容。
3. **原型定界面**：每个原型页面至少对应一行前端任务；页面内的独立交互（筛选、分页、导出、表单）
   体现在任务说明和档位里，不单独拆行，除非它本身是独立的可交付单元。

**数据类工作不单独拆行**：存储建模、索引、数据导入导出、对账与同步这类工作已经包含在后端任务里
（接口、业务逻辑、异步等任务类型），在任务说明与任务出处里写清领域模型与数据处理内容即可，
不为它们单独开一行，也不另找「数据」类子任务类型。

三类输入都没有覆盖的工作（运维手册、发布方案、交接等）依据项目实际需要补，
补进来的行同样要落到基线子任务类型。

## 2. 子任务类型与档位

基线的子任务类型已经拍平：每个任务类型有三行，`简单 xxx` / `普通 xxx` / `复杂 xxx`，
例如 `普通CRUD新建`。子任务类型名称就是查基线的键。

基线以「一个实体的一次完整增删改查」为锚点：前端与后端取同一套锚点人天，其余任务类型都是这个锚点的
倍数。锚点值、各任务类型的倍数关系与三档系数都写在基线工作簿里（「估算参数」表的锚点与档位系数行，
「基线任务类型」表的备注列记录推导），本文不复述具体数值。

选档分两步：

1. **先定任务类型**：按交付物判断落在哪个任务大类与任务类型（页面、字段、组件、接口、业务逻辑、
   异步、异常、系统对接、权限安全、平台能力、工程化应用等，以基线实际目录为准）。
2. **再定档位**：用该对象在本项目中的实际规模，对照基线同一行「评估标准」里
   `简单：` / `普通：` / `复杂：` 三段说明，逐条比对后落档。

规则：

- 档位判定必须能引用基线「评估标准」里对应档次的说明，不能凭感觉；
- 判定不了时取「普通」并在备注写明「档位待确认」；
- 跨档时以对象的主要特征为准：字段数量、页面数量、关联对象数量、校验复杂度、数据量、
  是否跨系统、是否含状态流转；
- 计量单位写在基线「备注」里（每组页面、每字段、每应用、每业务事务……），
  数量按该单位计算：同一子任务类型出现多次时按实例计数拆成多行，或用「数量」表达。

基线里没有对应子任务类型时，按 [未覆盖处理](#7-基线未覆盖的处理) 处理，不自造类型。

## 3. 修正因子

基线「修正因子」给出场景与系数区间。使用时：

- 在估算结果里同时给出「修正场景」和「修正系数」；
- 系数必须落在该场景的区间内，超出区间时脚本告警；
- 只给场景不给系数时，脚本取区间下限并告警，需要人工确认后补写；
- 遗留系统改造用「修正场景 = 在遗留系统中增加功能」表达，不再单列工作方式。

修正因子只处理「同类工作在特定环境下更贵」这一层，不改变任务类型与档位判断。

**集成类任务类型例外**：「集成」大类的基线行已经按对接复杂度分档，再乘修正系数会重复计算。
命中集成类任务类型时脚本忽略该行的修正场景与修正系数，并在告警里说明；
对接规模、对方是否需要定制开发等差异体现在选档上。

## 4. 设计与测试的派生

基线只保存开发人天。设计与测试由基线「估算参数」里的换算系数派生：

```text
开发人天 = 基线[子任务类型] × 修正系数 × 数量
设计人天 = 开发人天 × 设计换算系数
测试人天 = 开发人天 × 测试换算系数
```

换算系数是项目级参数，需要按团队实际投入结构调整时改基线文件；基线里没有这些参数时脚本直接报错。

需要偏离换算系数时，在估算结果的「人天分配」里直接给出三列人天，脚本以给定值为准。

## 5. 项目级开销

「项目汇总」的两项开销按基线参数换算：

- 交付开销 =（设计 + 开发 + 测试）× 交付开销系数
- 项目管理开销 =（设计 + 开发 + 测试）× 项目管理开销系数
- 合计 = 设计 + 开发 + 测试 + 交付开销 + 项目管理开销

交付开销覆盖发布、UAT、验收、文档整理与迁移演练这类不落在单个子任务类型上的工作；
项目管理开销覆盖全程项目管理活动。开销系数只是起点，需要按项目实际情况在基线文件里调整。

## 6. 三列的语言分工

评估模板的前三列各有固定读者与固定写法：

- **需求列用业务语言**：照 PRD 章节的业务表述写，读者是业务方；
  在「需求出处」里写清 PRD 章节或需求编号。
- **任务说明列用技术语言**：写领域模型、接口路径、数据处理与原型页面等实现细节，读者是技术方；
  在「任务出处」里写清 HLD 章节、接口路径或原型文件。
- **任务类型列用完整路径**：由脚本按基线拼成 `任务大类-任务类型-子任务类型`，
  例如 `前端-页面-普通CRUD新建`，用来回查基线。

业务表述不要混进接口名与表名，技术表述不要复述业务价值。两列互相看不懂时，说明该行拆分过粗。

## 7. 基线未覆盖的处理

基线里找不到对应子任务类型时：

1. 先确认是不是拆解粒度不对——多数「未覆盖」其实应该落到某个已有类型；
2. 确实没有对应类型时，在估算结果的「子任务类型」写最接近的基线名称并在备注标注
   「基线未覆盖：<原因>」，人天按 0 计并在报告告警中列出；
3. 需要补基线时，由用户在基线工作簿「基线任务类型」中追加该任务类型的三档行
   （任务大类、任务类型、子任务类型、基准人天、备注、评估标准、示例场景），
   档位按简单 / 普通 / 复杂成组补齐；普通档人天按基线锚点的倍数换算，再重跑生成。

不要在估算结果 JSON 里直接写人天数字绕过基线，也不要修改基线工作簿的既有行来迁就单次估算。
